## 조사 규율 (실패 사례에서 도출)

종합·판정의 품질은 조사 단계 입력의 정확도에 전적으로 의존한다. 실제 운용에서
**추측 기반 오진이 반복 발생**했으므로 아래를 강제한다:

- **소스를 열기 전에 진단하지 않는다.** "아마 이럴 것"이라고 말하는 순간
  틀린 전제가 판정 단계로 전파된다. 스크립트·설정·로그를 실제로 읽고 말하라.
- **문서에는 유효기간이 있다.** 요약 문서(`00_summary` 류)는 대개 오래되었고,
  최신은 diff 문서나 실제 소스(tex/코드)다. **요약만 보고 "미반영"이라 판정하지 말 것.**
- **데이터가 가설을 반박하면 가설을 버린다.** 코드를 읽고 세운 가설이라도
  통계가 반대 방향이면 즉시 폐기하고 재수립하라.
- **검증 수치가 나쁘게 나오면 데이터보다 먼저 검사 자체를 의심한다.** 위 항목의
  반대 경우다. 2026-08-07 성경 본문 정합성 검증에서 "정답어가 본문에 있는가"를
  기계로 쟀더니 46.6% → 58.8% → 83%로 올라갔는데, **매번 원인은 데이터가 아니라
  내 필터의 결함**이었다(부정형 문항은 정답이 본문에 없는 게 정상, "이 구절은 어느
  책인가" 문항은 책 이름이 본문에 없음, 쉼표로 나뉜 다중 빈칸을 통째로 대조).
  마지막 83%의 잔여 17%도 정답이 그 대목의 **화자**여서 본문이 "내·그"로 지칭한
  경우였다 — 실제 오류는 0건이었다. **낮은 수치를 보고하기 전에 불일치 표본을
  10건쯤 눈으로 읽어라.** 표본을 읽지 않고 수치만 말하면 멀쩡한 데이터를 의심하게 만든다.
- **긁어온 원본은 파싱 결과와 함께 보관한다.** 파서를 고칠 때마다 다시 받게 된다.
  같은 날 성경 본문 1,017장을 각주·소제목을 걷어내느라 **14분씩 두 번** 다시 받았다.
  원본을 gzip 으로 두면(1,017장 = 8.6MB) 재파싱이 몇 초고, 남의 서버도 덜 두들긴다.
  스크레이핑 스크립트에는 `reparse` 류의 무네트워크 재처리 경로를 처음부터 넣어라.
- **용량 측정은 논리크기(`stat %z`)와 실제블록(`du`)을 구분한다.** iCloud·클라우드
  최적화 저장 환경에서는 파일이 클라우드에만 있고 로컬 블록이 비어 `du`가 **0으로
  보인다**(내용은 멀쩡). 2026-08-06 iCloud 용량 분석에서 이걸 놓쳐 "17GB→5GB"·"백업
  0B" 등으로 두 번 오측했다. 미다운로드 파일이 섞인 곳의 용량은 두 값을 함께 확인하고,
  "회수 가능 용량"을 말하기 전에 실제 다운로드 여부를 본다.
- 오진했으면 **정정 이력을 문서에 남긴다**(WORKLOG 등). 같은 실수의 재발을 막는다.
- **이전 세션의 마지막 발언을 현재 상태로 믿지 않는다.** 그 발언은 그 세션이 시작될
  때의 컨텍스트로 말한 것일 수 있다. 실제로 8/4 세션이 7/17 컨텍스트 그대로
  "내일 촬영"이라고 끝냈는데 촬영은 이미 2주 반 전에 끝나 있었다. 상태는 발언이 아니라
  **파일 mtime과 현재 날짜**로 교차검증한다.

## 병렬 세션 주의

여러 서버·창에서 동시에 작업하면 다음이 실제로 발생한다:

- **중복 노동**: 다른 세션이 같은 수정을 이미 커밋해 `git commit`이 "nothing to commit"으로
  끝난다. **세션 시작 시 `git log`·`git status`로 HEAD와 워킹트리를 먼저 확인하라.**
- ⚠️ **`git status`만으로는 원격 이탈을 못 본다. `git fetch`가 먼저다.**
  fetch 전의 `git status`는 낡은 로컬 `origin/main` ref를 기준으로 "up to date"라고
  보고한다. 워킹트리가 깨끗해도 원격이 앞서 있으면 push가 거부된다(실제로 발생).
  공유 리포를 건드리기 전에는 항상:
  `git fetch -q && git rev-list --left-right --count HEAD...@{u}`
  (출력이 `2  2` 면 양쪽이 갈라진 것이다. 병합 전에 `git branch -f backup-<날짜> HEAD`로
  백업 ref를 만들고 rebase한다. 충돌하면 `git rebase --abort`로 되돌린다.)
- **미커밋 수정 유실 위험**: 워킹트리에 남은 수정은 다른 세션이 덮어쓸 수 있다.
- ⚠️ **같은 기계의 다른 세션이 로컬 커밋하면 `git status`도 `git fetch`도 못 잡는다.**
  원격과 갈라진 게 아니라 같은 로컬 저장소를 공유하는 상황이라 이탈 카운트가 `0 0`으로 나온다.
  `git reflog`에 내가 하지 않은 `commit:` 항목이 있으면 그것이 다른 세션이다.
  하네스가 띄우는 "modified, either by the user or by a linter" 알림도 **실제로는
  다른 세션의 수정일 수 있다**(2026-08-06 실측). 하네스는 수정을 감지하되 주체는 구분하지 못한다.
  → 공유 리포를 여러 번 편집하는 세션에서는 **편집 직전마다 `git log --oneline -3`**으로
  HEAD가 그대로인지 확인한다.
- **자동화와의 충돌**: 큐 러너·감시 스크립트가 있으면 프로세스 kill을 "완료"로 오인해
  후속 작업을 조기 투입한다. 실행 중 프로세스를 죽이기 전에 감시자를 확인하라.

→ 장시간 작업은 **WORKLOG(append-only) + 메모리**에 남겨 세션 간 상태를 공유한다.

**열려 있는 세션을 확인하는 세 가지 방법** (셋은 서로 다른 것을 보여준다. 숫자가 안 맞는 게 정상):

| 방법 | 범위 |
|---|---|
| 앱 왼쪽 목록 = `list_sessions` 도구 | **계정 전체(기계 4대)**. 죽어 있어도 표시된다 |
| 아래 `pgrep` | 그 기계에서 **지금 프로세스가 살아 있는** 것만. 충돌 판단에는 이게 가장 정확 |
| `~/.claude/projects/**/*.jsonl` | 그 기계 디스크의 트랜스크립트 전부. 닫힌 세션도 포함(VSCode 확장이 보는 것) |

```bash
for p in $(pgrep -f '/\.claude/remote/ccd-cli/'); do [ -d /proc/$p ] || continue; case "$(tr '\0' ' ' </proc/$p/cmdline)" in *ugrep*) continue;; esac; printf '%-8s %-17s %s\n' "$p" "$(ps -p $p --no-headers -o lstart= | cut -c5-20)" "$(readlink /proc/$p/cwd)"; done
```

⚠️ `pgrep -x claude`는 **아무것도 못 잡는다.** 프로세스 이름이 `claude`가 아니라
실행파일명인 버전 번호(`2.1.221` 등)다. 원격 접속 구조라 경로는 `~/.claude/remote/ccd-cli/`.
검색 도구(`ugrep`)가 같은 경로에서 실행돼 매칭에 걸리므로 제외 조건이 필요하다.

## 장시간 작업 — 진행경과·잔여시간을 항상 보여준다

**수 분 이상 걸리는 작업은 진행률과 잔여시간을 볼 수 있어야 한다.** 사용자가
"얼마나 남았어?"라고 물었을 때 답이 **경과시간 외삽뿐이면 그건 계기가 없는 것**이다.

### 1. 실행 전 — 관측 가능하게 만들고 시작한다

- 반복 루프(round·epoch·batch·item)가 있으면 **매 반복을 로그로 남긴다.**
  형식: `<i>/<N> ... | <경과>분 경과, 잔여 ~<eta>분`. eta는 `경과/i × (N-i)` 선형 외삽으로 족하다.
- ⚠️ **진행 로그가 있는데 꺼져 있는 경우가 실제로 많다**(`progress=False`, `verbose=0`,
  기본이 조용한 라이브러리). *"로그가 없다"고 단정하기 전에 스위치부터 찾을 것* —
  없는 걸 만들기보다 꺼진 걸 켜는 경우가 훨씬 흔하다.
- 로그 줄 수가 부담이면 주기를 늘린다(매 N회). **끄지는 않는다.**
- 파이프로 넘길 땐 **버퍼링을 끈다**(`python -u`). 안 그러면 끝날 때까지 로그가 안 보여
  "진행이 없다"로 오인한다.

### 2. 실행 중 — 진행바를 그리되 근거를 밝힌다

- **1순위는 로그의 실제 진행**이다. 로그에 진행이 없으면 경과시간 + 기준 소요시간으로
  추정하되 **"추정치"라고 반드시 표시**한다. 근거가 다른 두 수치를 같은 얼굴로 보이지 말 것.
- 프로세스를 찾을 땐 `pgrep -f`가 **자기 명령줄까지 매칭**한다. 로그 파일을 실제로 쥔
  프로세스만 잡으려면 `/proc/<pid>/fd`의 실경로를 대조한다.
- 자원도 함께 본다. **동시 실행 수를 CPU 코어만 보고 정하지 말 것** — 메모리가 먼저 터진다
  (커널이 조용히 죽이면 "그냥 안 끝났다"로 보인다).

### 3. 시간을 말했으면 **반드시 확인하러 돌아간다**

"약 30분 남았습니다"라고 말해 놓고 확인하지 않는 것은 **틀린 추정보다 나쁘다.**
완료 마커를 기다리는 감시를 걸어 두고, 끝나는 즉시 결과를 보고한다.

> 이 규칙은 사후 진단이 아니라 **선행 조건**이다. 오래 걸릴 것을 알면서 계기 없이
> 시작하면, 끝날 때까지 사용자도 나도 아무것도 알 수 없다.

⚠️ 이건 **행동 규칙이라 훅으로 강제되지 않는다.** `settings.json`은 명령을 가로챌 뿐
루프 안에 로그를 넣어 주지 못한다. 규칙으로 지킬 것.

### 4. ★ 완료 알림 전에 산출물 파일을 읽지 마라 (2026-08-03 실측)

백그라운드 작업·서브에이전트의 결과 파일을 **완료 통지 전에 읽으면 중간 상태를 본다.**
파일이 존재한다는 것이 작업이 끝났다는 뜻이 아니다.

- **실제 사례**: 에이전트 4개 중 3개가 끝나 보이자 나머지 하나의 출력을 미리 읽고
  "인용 149개 중 31개가 조각 밖 = 창작 의심"이라고 보고했다. **완료 후 다시 재니 인용 326개·이탈 0건**이었다.
  중간 저장본을 최종본으로 오인해 **멀쩡한 작업을 결함으로 신고**한 것이다.
- 같은 날 **서브에이전트도 같은 함정에 빠졌다** — 병합 작업 중 다른 프로세스가 입력 파일을
  재생성했는데, 그 에이전트는 작업 중 파일 변경을 감지해 다시 읽고 대응했다(스스로 보고함).
- **규칙**: ①완료 통지를 기다린다 ②굳이 중간 확인이 필요하면 **"작업 중이라 잠정치"라고 명시**한다
  ③여러 프로세스가 같은 파일을 쓸 수 있으면 **읽기 전 `ls -la`로 수정시각을 확인**하고,
  작업 중 바뀌었으면 다시 읽는다.
- 병렬 세션·병렬 에이전트가 흔해질수록 이 문제는 커진다. **파일 존재 ≠ 작업 완료.**

### 5. ★★ 중간 기록 파일을 진실로 취급하지 마라 (같은 함정 3회 반복)

"처리했다는 기록"과 "처리된 결과"는 다르다. **진짜 원본은 결과물 쪽**이다.

- **실측 3건** — 모두 같은 프로젝트에서, 다른 파일로, 세 번 당했다:
  - `.remaining_*.txt` — 작업 시작 시 만든 목록이 갱신되지 않아 "남은 1,863편"이라는 **오답**을 냈다(실제 63편).
  - `.new_videos.txt` — 그 주 수집분만 기록하고 **매주 덮어쓰므로**, 이전 주에 수집됐으나 반영 안 된 6편이 영영 빠졌다.
  - `done.txt` — 3,386편이 "처리 완료"로 적혀 있었지만 그중 **53편은 결과물에 아무것도 없었다**(11일치 통째 유실). 매주 돌리던 확인이 done.txt 기준이라 전부 통과했다.
- **처방**: 진행 상황은 **원천에서 매번 파생 계산**한다(예: `전체목록 − 결과물에실재하는것`).
  "기록 파일에 있으니 됐다"가 아니라 **"결과물에 실제로 있는가"**로 검사하는 감사 도구를 따로 만들고,
  자동화 스크립트에 물려 매 실행마다 돌린다. 문제 있으면 종료코드로 알린다.
- **조용한 실패라 더 위험하다.** 셋 다 에러 없이 "정상"으로 보고됐고, 사용자가 물어봐서야 드러났다.
