# 노션 작업 규칙

이 문서는 실패로 배운 것이다. 노션에 데이터를 넣거나 고치기 전에 읽는다.

## 1. 핵심 — MCP로 한글 대량 적재 금지

**Notion MCP 도구로 한글 텍스트를 대량 적재하면 4~12%가 손상된다.** 실측값이다(4,442행 중 248건 = 5.3%).

**원인**: MCP 도구 호출 인자는 **모델이 토큰으로 재생성**한다. 파일에서 Read한 값을 '그대로 넘기는' 경로가 **물리적으로 존재하지 않는다** — 파일과 도구 사이에 항상 모델의 전사(轉寫)가 낀다. 한글은 초성·중성·종성 조합으로 코드포인트가 계산되는데, 모델이 `\uXXXX`를 손계산하다 종성을 틀린다. 그래서 **받침만 어긋난다**:

- `영끌→영끔`, `돌아섰다→돌아섬다`, `끓→끌`, `곳→곧`, `퀄컴→퀵컴`, `쏠리는→쓸리는`
- **숫자·영문은 안 틀린다** (조합 계산이 없으므로)

**안 통하는 처방 (전부 시도했고 전부 실패):**

| 처방 | 결과 |
|---|---|
| '이스케이프 쓰지 말고 한글 그대로 써라' | 불가능 — 경로상 자동 직렬화됨 |
| '코드포인트를 손계산하지 마라' | 에이전트가 4번 선언하고 4번 실패 |
| '적재 후 검증해라' | 모델 육안 비교라 놓침. 뒤로 갈수록 악화(25건 중 14건 손상) |

**구조적 한계는 프롬프트로 못 고친다. 경로를 바꿔야 한다.**

## 2. 해법 — python이 REST API를 직접 호출

python이 파일을 읽어 HTTP로 보내면 **바이트가 그대로** 가서 손상이 구조적으로 불가능하다. 모델은 **코드만** 만들고 **데이터는 안 만진다**.

### 세팅 (기계마다 1회)

- 토큰: `~/.notion_token` (권한 600). **값을 대화창에 출력하거나 붙여넣지 말 것** — 트랜스크립트에 평문으로 남는다. 노출됐다면 즉시 Regenerate.

**★ 토큰을 파일에 넣는 안전한 방법.** 화면에도 셸 히스토리에도 값이 남지 않는다.

```bash
umask 077
printf '토큰 붙여넣고 Enter (화면에 안 보임): '; read -rs TOK; echo
printf '%s' "$TOK" > ~/.notion_token; unset TOK; chmod 600 ~/.notion_token
```

`read`에 **`-s`가 반드시 있어야 한다.** 2026-07-30에 `-s` 없이 안내했다가 입력값이 화면에 그대로 찍혔고, 사용자가 그 화면을 복사해 붙여넣으면서 토큰이 대화 기록에 평문으로 남아 재발급해야 했다.

**클립보드 함정도 있다.** `pbpaste > ~/.notion_token`(macOS)를 안내하면, 사용자가 그 명령어를 복사하는 순간 클립보드가 덮여서 토큰 대신 **명령어 텍스트가 파일에 들어간다.** 같은 날 세 번 반복됐다. 클립보드 경유를 안내하지 말고 위 `read -rs` 방식을 쓰거나, 이미 정상 동작하는 기계가 있으면 `scp`로 파일을 그대로 옮긴다.
- Notion 통합을 만들고 **Access token** 방식을 쓴다(OAuth 아님 — 정적 토큰이라 스크립트·cron에 적합).
- Capabilities: Read / Update / Insert content. User는 'No user information'.
- **연결 범위는 가능한 최상위 페이지**에 건다 — 하위 전체가 상속된다.

### 도구

이 저장소의 `~/claude-config/tools/notion_page.py` — 마크다운 파일을 노션 페이지 본문으로 적재한다.

```bash
python3 ~/claude-config/tools/notion_page.py plan            # 무엇을 어디에 넣을지 보기만
python3 ~/claude-config/tools/notion_page.py push <slug>     # 한 페이지 교체(전체 삭제 후 재적재)
python3 ~/claude-config/tools/notion_page.py append <slug>   # 끝에 이어붙이기(누적 페이지용)
python3 ~/claude-config/tools/notion_page.py verify <slug>   # 적재본 vs 로컬 글자단위 대조
```

페이지 매핑은 스크립트가 아니라 **프로젝트 디렉터리의 `notion_pages.json`** 에 둔다. 페이지 id는 프로젝트 정보이므로 공개 저장소에 올리지 않는다.

```json
{
  "pages": { "note": { "page_id": "32자hex", "file": "notion_content/note.md" } },
  "append_only": ["누적페이지슬러그", "사람이_채우는_페이지슬러그"]
}
```

지원 문법: `#`~`###`, 문단, `-` 불릿, `1.` 번호, `---`, `- [ ]` 체크박스, 인라인 `[텍스트](url)`·`**굵게**`. 표·코드블록은 미지원이니 필요하면 `md_to_blocks()`를 확장한다.

### API 호출 기본형 (직접 짤 때)

```python
import json, os, urllib.request
tok = open(os.path.expanduser('~/.notion_token')).read().strip()
H = {"Authorization": "Bearer " + tok,
     "Notion-Version": "2022-06-28",
     "Content-Type": "application/json"}
# 조회: POST /v1/databases/{db}/query   (page_size 100, next_cursor 페이징)
# 생성: POST /v1/pages
# 수정: PATCH /v1/pages/{page_id}
# 블록: GET/PATCH /v1/blocks/{id}/children   (append 시 after 로 위치 지정 가능)
```

429/5xx는 **지수 백오프**, 요청 간 **0.34초**(약 3 req/s).

## 3. ★ 조용한 실패 네 가지 — 이게 가장 위험하다

에러를 내면 알아채지만, 조용히 틀리면 그 말을 믿고 다음 행동을 한다.

**① 조회가 10,000행에서 거짓 종료한다.** 필터 없이 커서로 끝까지 돌리면 정확히 10,000행에서 `has_more:false`로 멈춘다. 에러가 아니다. 실제로 audit이 'DB 10,000행 / 미적재 1,298'이라고 멀쩡히 보고했고, **그 말을 믿고 재실행했으면 1,298건 중복을 만들 뻔했다.** 진짜 값은 11,299였다.
→ **카테고리·연도 등으로 분할 조회**하고, 한 구간이 상한에 닿으면 예외를 던져 중단시킨다. 딱 떨어지는 숫자가 나오면 의심하라.

**② 200을 반환하면서 실제로는 무시되는 요청이 있다.** 페이지의 `parent` 변경을 `PATCH /v1/pages/{id}`로 보내면 200이 오지만 부모가 안 바뀐다(API 버전에 따라 다름).
→ **쓰기 후에는 재조회해서 확인**한다. 응답 코드를 믿지 않는다. 이 경우는 MCP `notion-move-pages`로 처리하면 된다.

**③ 페이로드가 조용히 잘린다.** MCP `create-pages`는 50행(약 44KB)에서 `InputValidationError`. 25행(약 13KB)이 안전선. 스크립트에는 이 한계가 없다.

**④ 뷰 필터 DSL이 표현하지 못하는 조건을 조용히 버린다.** MCP `update-view`의 `configure`에 `FILTER "상태" != "Done"`처럼 **status 타입** 조건을 주면 200이 오고 응답도 정상으로 보이지만, 저장된 config에는 조건이 없는 **빈 그룹**(`filters: []`)만 남는다. 지시문을 나눠 보내도(`FILTER a; FILTER b; FILTER c`) 같다. `CLEAR FILTER`도 UI로 만든 기존 `simpleFilters`는 지우지 못한다. select 조건은 정상 저장되므로, **일부만 반영되고 일부는 사라진 상태**가 조용히 만들어진다.
→ 결과적으로 필터가 `simpleFilters`(UI 생성분)와 `advancedFilter`(DSL 주입분) **두 곳에 쪼개져** 남는다. 실측(2026-08-07) 결과 둘은 **AND로 결합**되어 동작은 한다. 다만 config만 봐서는 어느 조건이 살아 있는지 알기 어렵다.
→ **응답 config를 반드시 눈으로 훑고, 빈 `filters: []` 그룹이 보이면 그 조건은 죽은 것이다.** 최종 판정은 행 수로 한다. 100행씩 페이징이 부담이면 **정렬을 잠깐 바꿔 검증 대상(제외됐어야 할 값)을 맨 앞으로 보내고 `page_size: 3`으로 조회**한 뒤 정렬을 원복하면 한 번에 끝난다. 원래 정렬값은 바꾸기 전에 적어 둔다.
→ status 조건은 DSL로 넣을 수 없다. **노션 UI에서 직접** 걸거나, 기존 simpleFilter를 건드리지 말고 DSL로는 select 조건만 얹는다.

**에러 구분**: `InputValidationError`는 Notion **미도달**이라 재시도해도 중복이 없다. **연결끊김·타임아웃은 이미 생성됐을 수 있어 재시도 금지** — 총행수 산술로 먼저 확인한다.

**중복은 사후 진단이 아니라 설계로 막는다.** 행 적재기는 멱등하게 만든다. 적재 전에 대상 필터로 기존 행의 고유키(제목 등) 집합을 읽고, 이미 있으면 건너뛴다. 이러면 중간에 끊겨도 재실행이 안전하고, 원본 파일에 항목을 추가한 뒤 다시 돌리면 새 것만 들어간다. ①의 사고도 적재기가 멱등했다면 재실행이 무해했을 것이다.

## 4. push는 파괴적이다

`push`는 기존 블록을 전부 삭제하고 다시 넣는다(= regenerate). **사람이 값을 채워 넣는 페이지나 누적 페이지에 쓰면 그 내용이 사라진다.**

- 그런 페이지는 `notion_pages.json`의 `append_only`에 넣어 스크립트 레벨에서 막는다.
- 부분 수정은 `PATCH /v1/blocks/{block_id}`로 **블록 단위**로 한다.
- 사용자가 쓴 텍스트에 무언가를 덧붙여야 하면, 기존 `rich_text` 배열을 읽어 **뒤에 새 run만 append**한다. 문자열을 다시 타이핑하지 않는다.
- 블록 삭제는 하나씩만 된다(호출당 0.34초). 수백 블록이면 수 분 걸리니 백그라운드로 돌린다.

### ★ select·multi-select 옵션 추가도 '전체 재전송'이다

옵션 하나만 추가하는 경로가 API에 없다. `PATCH /v1/databases/{id}`에 **기존 옵션 전부와 새 옵션을 함께** 보내야 하며, 빠뜨린 옵션은 삭제된다. 여기서 1절의 손상이 그대로 재현되는데, 이번에는 행 값이 아니라 **분류 체계가 깨진다.** 기존 옵션명을 모델이 다시 타이핑하다 받침 하나가 어긋나면, 그 옵션을 쓰던 기존 행들이 다른 값으로 분리된다.

- `GET /v1/databases/{id}`로 읽은 `{name, color, id}`를 **python이 그대로 재전송**하고 새 옵션만 append한다. 기존 이름은 모델이 만지지 않는다.
- PATCH 후 재조회해서 **옵션 수가 정확히 +1인지, 기존 이름이 그대로인지** 확인한다(3절 ② 규칙).
- 스키마 파악(프로퍼티 타입, select 옵션 목록, 데이터소스 id)은 MCP `fetch`가 빠르다. **파악은 MCP, 쓰기는 REST**로 나눈다.

실측(2026-08-05): 옵션 1개 추가 후 44행 적재, 프로퍼티 단위 대조 일치, 손상 0 / 미적재 0 / 중복 0.

**★ 색은 만들 때만 정할 수 있고, 옵션 삭제는 값을 조용히 비운다.**

- **색은 생성 시점에만 지정된다.** 이미 있는 옵션의 `color` 를 바꿔 PATCH 하면
  `Cannot update color of select with id: ...` 400 이 난다. **옵션을 만들 때 색을 함께 준다.**
- **되돌리려면 지웠다 다시 만들어야 하는데, 삭제는 그 값을 쓰던 행의 값을 에러 없이 비운다.**
  그래서 색을 안 주고 만든 옵션은 사실상 **되돌릴 수 없는 기본값으로 굳는다**(UI 에서 손으로
  바꾸는 것 말고는 경로가 없다).
- **옵션을 지우기 전에 그 값을 쓰는 행을 원천에서 센다.** 파생 계산으로 "이제 비었다"를
  유도하지 않는다(`rules/workflow.md` 「도구·에이전트 작성 규율」의 삭제 항목).

실측(2026-08-15): 새 분류 옵션 4종을 색 없이 만든 뒤 색을 넣으려다 400. 되돌리려면 그 값을
쓰는 68건이 비워지는 상황이라 색은 UI 에서 손으로 바꿨다.

## 5. 언제 스크립트, 언제 MCP

| 상황 | 선택 |
|---|---|
| DB 행·속성 **대량** 적재/수정/검증 | **스크립트** (압도적) |
| **마크다운 문서 → 페이지 본문** | **스크립트** (변환기를 갖춘 뒤로는 이쪽이 낫다) |
| 사용자가 **이미 로컬에 가진 .md 다발**을 페이지로 | **Notion 자체 Import(Markdown)** — Claude를 아예 안 거쳐 토큰 0·손상 0·원문 그대로. 속성은 임포트 후 스크립트로 채운다 |
| 같은 작업 반복, cron | **스크립트** |
| 정확한 텍스트가 생명 | **스크립트** |
| 탐색·검색·구조 판단 | **MCP** |
| 페이지·DB **이동**, 부모 변경 | **MCP** (`notion-move-pages`) — 텍스트 재타이핑이 없어 손상 위험이 원천적으로 없다 |
| 일회성 소량 작업 | **MCP** |

**원칙: 모델이 텍스트를 재타이핑해야 하는 경로면 스크립트로 우회한다. 판단·탐색·구조 조작이면 MCP를 쓴다.**

**세 번째 경로를 잊지 말 것.** 스크립트조차 파일을 읽어 HTTP로 보내지만, 사용자가 이미 디스크에 가진 마크다운 다발이라면 **Notion 앱의 가져오기(Import→Markdown)로 드래그하는 것이 가장 싸고 안전하다** — 바이트가 Notion 서버로 직행해 Claude도 스크립트도 거치지 않는다. 2026-08-06, 강의 자막 21개(~57만 자)를 MCP로 올리려다 이 경로가 최선임을 확인했다. 단 DB 속성(과목·태그 등)은 임포트가 못 채우니, 임포트 후 속성만 스크립트로 채운다(속성은 텍스트 재타이핑이 적어 저렴).

과거에는 '마크다운→페이지는 MCP가 낫다'고 적혀 있었다. MCP가 블록 변환을 공짜로 해주기 때문이었는데, `md_to_blocks()`를 한 번 만든 뒤로는 그 이점이 사라졌다. 실측으로 24만 자를 손상 0으로 적재했다.

## 6. 검증은 어느 방식이든 필수

적재 후 **반드시 재조회해서 로컬과 글자 단위로 대조**한다. 기계적 방식에서도 손상이 1건 나온 적이 있고, 그건 검증에서 잡혔다.

- 탐지는 **프로그램 대조**로 한다(고유키로 묶고 최유사 짝짓기 → 글자 diff). **육안 비교는 놓친다.**
- `verify`가 로컬을 정규화할 때 **줄당 접두사를 하나만** 벗겨야 한다. `## 1. 제목`에서 `## `를 벗기고 남은 `1. `까지 벗기면 멀쩡한 노션을 불일치로 오판한다(실제로 겪음).

## 7. 404가 나면 — 통합 연결부터 의심

토큰이 맞아도 **통합이 그 페이지에 연결돼 있지 않으면 404**(`object_not_found`)다. 노션은 명시적으로 연결된 페이지만 API에 노출한다.

### ★ 접근 경로가 두 개다 — 범위가 서로 다르다

| 경로 | 인증 | 보이는 범위 |
|---|---|---|
| REST 토큰(내부 통합) — 이 스킬이 쓰는 것 | `~/.notion_token` | **명시적으로 연결된 페이지만** |
| MCP 커넥터 | OAuth | **워크스페이스 전반** |

2026-08-06에 MCP 커넥터로 제목 검색을 한 번 했더니 사용자가 Claude에게 보이고 싶지 않던 개인 페이지가 그대로 잡혔다. 위 404 절은 **REST 경로만** 설명하므로, 가시성·차단을 안내할 때 이 절만 근거로 "연결된 페이지만 보인다"고 말하면 틀린다. **두 경로를 모두 짚어야 한다.**

⚠️ 커넥터를 `permissions.deny`로 막으려면 서버 식별자(UUID)가 필요한데, 그 값이 `~/.claude.json`·`settings.json` 어디에도 저장돼 있지 않다(2026-08-06 확인). 세션마다 부여되는 값이면 규칙이 다음 세션에서 안 맞는다 — **미검증이므로 "차단됨"이라고 단정하지 말고 다음 세션에서 UUID가 같은지 재확인한다.**

**연결 방법(사용자가 노션 UI에서 직접)**: 대상 페이지 열기 → 우측 상단 `···` → `Connections`/`연결`/`Add connections` 중 보이는 것 → 통합 검색 후 승인. 메뉴가 길면 끝까지 스크롤한다(버전마다 이름·위치가 다름).

**진단**: `POST /v1/search`가 하위 항목만 뱉고 상위 페이지가 404면 연결이 하위에만 걸린 것이다. 상위에 다시 연결하면 전체가 열린다.

### ★★ 인증 확인과 접근 확인은 다르다 — 반드시 대상 페이지로 검사할 것

`GET /v1/users/me`가 200이어도 **원하는 페이지에 못 닿을 수 있다.** 그건 토큰이 살아 있다는 뜻일 뿐 연결 여부와 무관하다. 2026-07-30에 이걸로 '토큰 아직 유효'라고 보고했다가, 실제로는 대상 페이지가 전부 404인 상태였다. 그 오진 때문에 사용자가 토큰을 재발급하고 여러 번 다시 넣는 헛수고를 했다. **원인은 처음부터 토큰이 아니라 연결이었다.**

토큰을 바꾸거나 통합을 바꾼 뒤에는 **실제로 쓸 페이지·DB에 GET을 날려** 확인한다.

```python
import os, urllib.request, urllib.error
t = open(os.path.expanduser('~/.notion_token')).read().strip()
H = {'Authorization': 'Bearer ' + t, 'Notion-Version': '2022-06-28'}
TARGETS = [('pages', '<page_id>', '최상위 페이지'),
           ('databases', '<db_id>', '대상 DB')]     # 프로젝트 notion_pages.json 에서 가져온다
for kind, pid, name in TARGETS:
    try:
        urllib.request.urlopen(urllib.request.Request(
            'https://api.notion.com/v1/%s/%s' % (kind, pid), headers=H))
        print('OK  ', name)
    except urllib.error.HTTPError as e:
        print('FAIL', name, e.code)      # 404 = 연결 안 됨, 401 = 토큰 자체가 무효
```

**401과 404를 구분하라.** 401은 토큰 문자열이 잘못된 것(재발급·재입력), 404는 통합이 그 페이지에 연결되지 않은 것(노션 UI에서 연결)이다. **둘의 처방이 정반대**이므로 섞으면 엉뚱한 곳을 고치게 된다.

그리고 **User capabilities를 'No user information'으로 두면 `/v1/users/me` 자체를 못 쓴다.** 권한을 최소로 주는 것이 맞으므로, 확인 수단으로 그걸 쓰지 말아야 할 이유가 하나 더 있다.

## 8. MCP 쿼터

MCP `notion-query-data-sources`(SQL)는 플랜 무료 쿼터가 있어 소진되면 `entitlement_required`(retryable:false)로 **완전 차단**된다(Business 플랜 필요). `notion-query-database-view`는 쿼터가 분리돼 살아있다. **REST API 직접 호출이면 이 문제 자체가 없다.**
